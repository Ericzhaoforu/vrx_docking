# Repository Working Notes

This repository is the `safe-docking-dev` development branch of the official VRX
Humble codebase. Work should stay on the current branch and inside this
repository; do not switch branches, rebase, or reset unless explicitly asked.

Persistent project context lives in
`docs/codex_context_safe_bay_autonomous_docking.md`. Read that file before
larger safe-docking changes.

Safe docking work should stay modular:

- Keep original VRX worlds, models, launch files, and task behavior usable.
- Add new safe-docking assets with clear `safe_docking` or `dock_2026_safe`
  names instead of modifying the original scan-dock-deliver task in place.
- Reuse VRX WAM-V, marine environment, launch, sensor, dock geometry, and bay
  containment infrastructure.
- Do not implement perception, planning, control, or evaluator behavior until
  the simulation milestone is visually launchable and verified.
- Future autonomy must not consume ground-truth dock pose, target bay index,
  bay detector topics, evaluator state, or Gazebo entity poses. Ground truth is
  acceptable only for evaluator/scoring code.
- Keep changes small and reviewable, with launch/test instructions documented
  in summaries or task docs.


# AGENTS.md MINCO-USV Addendum

## MINCO-USV implementation rules

When working on the MINCO-USV trajectory generator, follow these rules in addition to all existing repository instructions.

1. Read `docs/final_minco_usv_formulation_and_codex_plan.md` before editing code.
2. Implement strict GCOPTER-style MINCO-S3NU for the USV flat output
   \[
   z = [x, y, \psi]^T.
   \]
3. The outer optimization variables are only:
   - intermediate points `q_1, ..., q_{M-1}`;
   - time variables `theta` or positive segment times `T_i`.
4. Polynomial coefficients are not optimization variables.
5. Polynomial coefficients must be generated by the MINCO-S3NU linear system:
   \[
   A(T)c = b(q,H,G).
   \]
6. The original trajectory optimization objective contains only:
   - minimum-jerk smoothness;
   - optional total-time regularization when total time is not fixed.
7. Lateral generalized force, velocity, acceleration, and actuator bounds are constraints in the original problem. In the implementation they enter the unconstrained MINCO objective as dense quadrature penalties.
8. The lateral generalized-force bound must be configurable:
   \[
   |\tau_v(t)| \le \bar{\tau}_v.
   \]
   Use continuation: start with a loose `tau_v_bar`, then tighten gradually.
9. Include actuator constraints through the differential-thrust mapping:
   \[
   T_L = \frac{1}{2}\left(\tau_u - \frac{\tau_r}{l}\right),
   \qquad
   T_R = \frac{1}{2}\left(\tau_u + \frac{\tau_r}{l}\right),
   \]
   and enforce
   \[
   T_{\min} \le T_L,T_R \le T_{\max}
   \]
   through dense quadrature penalties.
10. Do not add input-effort, allocation-effort, velocity-cost, acceleration-cost, or guide-cost terms to the first MINCO objective. If diagnostics show these are needed, stop and report before adding them.
11. Do not implement front-end planning, obstacle corridors, ESDF costs, or NN residual compensation in this task unless explicitly requested.
12. Do not replace the existing flatness-MPC/NMPC tracker.
13. Do not implement PID fallback.
14. The estimator provides only `z` and `z_dot`; it does not provide `z_ddot`. Boundary acceleration must come from a boundary-acceleration policy: previous accepted MINCO trajectory, previous NMPC prediction, nominal last-command estimate, or zero for first run.
15. Run unit tests after each phase. Report PVA residuals, continuity residuals, gradient-check error, `tau_v` metrics, velocity/acceleration violations, and actuator-bound violations before claiming success.
16. Stop after three focused repair attempts on a failed phase and write a failure analysis instead of continuing.
